# Coverage and Professional Help

Capability records track coverage, evidence, execution gaps, and validation completeness. They do not classify the user's problem or select the repair.

The core audit implementation directly owns responsibility, trigger/description, instruction quality, rule governance, structure/resources, agent-instruction relationships, actual implementation integrity, behavioral evidence, regression evidence, evidence collection, and Gate adjudication. These are not fake Preferred Provider entries.

Codex may select any installed domain Skill when its instructions and the target make it relevant. The selection is explicit and open-ended; there is no security/PDF/frontend/etc. whitelist in the Engine. A target may also declare an open capability name. If that capability has no executed implementation, validation is `INCOMPLETE`.

Fallback equivalence remains an internal resilience mechanism for an installed Provider that actually attempted execution and failed. Absence of a required standard Skill is a dependency-preflight condition, not Provider failure, and cannot silently select a full fallback.

`deliverable_contract` is governed by inspection applicability. `NOT_REQUIRED` contributes full coverage without Provider execution; `OPTIONAL` may preserve validation success but missing execution makes coverage partial; `REQUIRED` makes absent, failed, stale, or invalid Provider evidence a required execution gap. Omitted applicability is legacy `COMPATIBILITY`, which remains usable but cannot become `AUDIT_COMPLETE_VALID`. A complete result must prove every implemented output's declaration, exposure, dispatch, artifact generation, behavioral coverage, and current Provider provenance; `target_self_report` is advisory only.

The baseline capability index is immutable for the operation. Coordinated deletion of a declaration, implementation, entrypoint, template, schema, and test remains a capability removal because comparison uses the retained baseline rather than the candidate's self-description. Removed or narrowed IDs require exact user authorization plus compatibility impact, migration, and deprecation evidence; `BROKEN` and `UNVERIFIABLE` cannot be authorized away.
